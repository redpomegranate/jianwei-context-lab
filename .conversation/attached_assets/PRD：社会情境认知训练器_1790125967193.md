我不会先从“做一个什么工具”开始，而会先把你的需求拆成：**训练目标 → 行为闭环 → 用户摩擦 → 产品能力 → MVP → 数据沉淀 → 后续智能化**。你真正要的不是“人际分析 App”，而是一个能长期提高你判断质量的 **社会情境认知训练器**。

下面我直接把目前需求转换成一版可以拿去继续做产品设计的 PRD v0.1。

# PRD：社会情境认知训练器

**暂定产品名：见微 / Context Lab**
**版本：v0.1**
**产品阶段：概念验证 → MVP**

# 1. 产品背景

用户希望提升自己在现实生活中的以下能力：

- 更准确地理解他人的行为；
- 更好地判断复杂人际关系和组织局势；
- 从有限信息中提取关键上下文；
- 避免“凭感觉下结论”；
- 能够提出多个合理解释；
- 对后续行为进行概率预测；
- 根据真实结果持续修正自己的判断模型；
- 将《资治通鉴》《史记》《红楼梦》等经典中的案例，逐渐迁移到现代现实场景。

当前主要困难不是缺乏知识，而是：

用户不知道现实中应该观察什么，也不知道如何系统记录、分析和复盘。

因此产品目标不是提供“识人技巧”，而是帮助用户建立一套可训练、可验证、可持续迭代的社会认知系统。

# 2. 核心产品定义

本产品不是：

“帮用户判断别人到底在想什么。”

而是：

> **帮助用户在现实场景中进行结构化观察、提出多个假设、做出可验证预测，并通过反馈持续校准自己的判断。**

核心模型：

**Context → Observation → Hypothesis → Prediction → Outcome → Update**

即：

上下文
↓
客观观察
↓
多个解释
↓
概率预测
↓
现实结果
↓
认知更新

产品的价值不是单次分析准确，而是让用户经过几十次、几百次真实事件后，逐渐形成更好的“内部世界模型”。

# 3. 用户问题拆解

当前需求实际上可以拆成六层。

| 层级     | 用户真正的问题           | 产品任务          |
| -------- | ------------------------ | ----------------- |
| 信息采集 | 我不知道应该注意什么     | 引导观察          |
| 信息加工 | 我容易把猜测当事实       | 强制事实/解释分离 |
| 推理     | 我经常只能想到一个解释   | 多假设生成        |
| 判断     | 我不知道哪个解释更可信   | 概率判断          |
| 验证     | 我的判断经常无法验证     | 生成具体预测      |
| 学习     | 错了以后也不知道错在哪里 | 复盘与长期校准    |

因此，产品不是一个功能，而是一条训练链。

任何功能如果不能进入这条链，都应该慎重加入。

# 4. 核心用户

## 初始用户

社会观察和组织经验相对有限，但希望主动提高判断能力的人。

典型特征：

有一定逻辑思考能力；

愿意复盘；

对心理、人性、历史、组织关系感兴趣；

经常意识到“事情发生以后才看明白”；

希望提前识别局势，而不是事后解释。

第一版本尤其针对：

**认知能力较强，但现实社会样本不足的人。**

# 5. Jobs To Be Done

用户真正雇佣这个产品完成的任务是：

> 当现实中发生一个让我感觉“这里可能有东西”的事件时，我希望快速记录，并被引导发现哪些信息重要，从而形成几个合理解释和可以验证的预测。

之后：

> 当事情发展出结果时，我希望知道自己当初哪里判断对了、哪里漏掉了信息，从而让下一次判断更准确。

长期：

> 我希望逐渐知道自己最容易在哪些社会情境中误判，以及哪些模式已经形成可靠直觉。

# 6. 核心产品原则

## 原则一：记录成本必须极低

用户真正生活中的场景发生非常频繁。

如果每次分析需要填写十五个字段，产品一定失败。

理想状态：

**30 秒记录，3 分钟分析。**

## 原则二：事实优先于解释

系统应不断帮助用户区分：

事实：

“他今天没有回复我的消息。”

解释：

“他对我不满。”

进一步推演：

“他准备疏远我。”

系统必须明确标记这三个层次。

## 原则三：禁止单一故事

产品应该主动阻止：

“因为 A，所以一定 B。”

默认要求至少产生：

Hypothesis A
Hypothesis B
Hypothesis C

目的不是增加复杂度，而是降低确认偏误。

## 原则四：预测必须可验证

禁止：

“感觉关系会变差。”

鼓励：

“未来 7 天，他主动联系我的次数可能低于过去平均水平。”

系统应该不断把模糊判断转换成可观察事件。

## 原则五：允许不确定

用户不能被训练成“什么都要解释”。

一个成熟判断应该允许：

未知。

例如：

A：40%
B：25%
C：15%
其他未知：20%

# 7. 产品核心闭环

用户遇到现实事件：

**① 快速记录**

↓

**② AI 帮助整理事实**

↓

**③ 提取关键 Context**

↓

**④ 用户先提出自己的解释**

↓

**⑤ AI 补充替代假设**

↓

**⑥ 用户做概率判断**

↓

**⑦ 产品生成可验证预测**

↓

现实继续发生

↓

**⑧ 用户补充结果**

↓

**⑨ 系统比较预测与现实**

↓

**⑩ 生成认知更新**

↓

进入用户长期个人模型

# 8. MVP 功能

MVP 不应该试图成为“人际关系操作系统”。

只解决一件事情：

> **完成一次高质量的现实事件学习闭环。**

## 8.1 Quick Capture

首页只有一个主要入口：

**“发生了一件事”**

点击以后支持：

文字输入；

语音输入；

非常短的记录。

例如：

“下午开会，领导之前说这个项目让我负责，今天会上突然让老王主导，我没搞懂为什么。”

AI 不立即分析。

首先整理成：

### 已知事实

领导此前表示项目由你负责。

今天会议中，由老王承担主导角色。

暂时未知是否发生正式职责调整。

### 用户推断

“领导是不是不信任我？”

系统明确告诉用户：

这是推断，不是事实。

# 9. Context Builder

系统随后只追问少量高信息价值问题。

不是固定问卷。

而是动态追问。

例如：

“这位领导以前临时改变负责人常见吗？”

“老王之前是否参与过这个项目？”

“近期是否发生过交付、质量或资源问题？”

“会议中领导具体用了什么措辞？”

目的不是收集所有信息。

而是：

**寻找最能改变判断概率的信息。**

这应该成为产品后期非常重要的智能能力：

### Information Gain

系统判断：

“下一个最值得问的问题是什么？”

# 10. Situation Model

系统自动生成当前局势模型。

示例：

### 人物

我
直属领导
老王

### 角色

我：项目执行者

领导：资源/任务分配者

老王：可能的新负责人 / 协同人员

### 当前事件

项目主导权出现变化。

### 关键未知变量

这是暂时协助还是正式替换？

变化来自领导自身判断还是更上层要求？

老王是否提前知道？

这一步是把现实中的混乱事件转化成结构化模型。

# 11. Hypothesis Engine

首先要求用户回答：

**“你现在觉得最可能是什么原因？”**

这是一个重要训练原则：

AI不能首先告诉用户答案。

否则用户不会形成自己的模型。

用户提交以后，AI再补充：

### H1

领导对执行质量存在担忧。

35%

### H2

老王拥有某种资源或经验，因此阶段性介入。

30%

### H3

上级临时调整任务分工。

20%

### H4

其他未知因素。

15%

AI还需要指出：

“目前证据不足以区分 H1 和 H2。”

# 12. Prediction Engine

每个主要假设必须产生预测。

例如：

如果 H1 成立：

未来两周领导可能减少核心任务授权。

如果 H2 成立：

老王介入完成某阶段后，你仍可能继续承担执行工作。

如果 H3 成立：

其他项目成员也可能出现类似调整。

系统最终要求用户选择：

### 我的当前预测

未来两周老王会继续主持该项目。

**概率：65%**

这成为真正可验证的训练数据。

# 13. Outcome Check

达到预测时间以后，系统提醒：

**“这件事情后来怎么样了？”**

用户只需要快速输入。

例如：

“老王主持了一周，后来领导又让我继续负责。”

系统重新打开原事件。

展示：

当时判断：

H1 35%
H2 30%
H3 20%

预测：

老王继续主持两周。

实际：

老王只短期介入。

然后进入复盘。

# 14. Reflection Engine

AI不能只说：

“预测错误。”

而应该分析：

### 当时哪些判断是正确的

你注意到了负责人变化，这是有效信号。

### 哪些地方过度推断

负责人变化被直接解释成了对你能力的不信任。

### 当时遗漏的重要变量

没有确认老王是否具有某种阶段性专业职责。

### 下一次遇到类似情况优先观察

任务变化发生之前，是否存在资源或专业需求变化。

这才是产品产生长期价值的位置。

# 15. Weekly Calibration

每周生成一份：

# 本周认知报告

不是统计“猜对多少次”。

重点包括：

### 本周最常见偏差

例如：

容易把他人的行为变化解释为针对自己。

### 经常忽略的信息

组织结构和资源约束。

### 判断最准确的领域

短期行为预测。

### 判断较弱的领域

对他人动机的推断。

### 本周出现的新模式

例如：

你连续三次低估了“领导本身也受上级约束”。

这会逐渐形成用户真正的：

**Personal Cognitive Model**

个人认知模型。

# 16. “观察模式”

这是非常适合产品差异化的功能。

用户进入某个现实场景之前可以打开：

**观察模式**

例如：

“我要参加部门会议。”

系统不会让用户记录所有东西。

而只给三个任务：

### 今天只观察三件事

谁提出问题？

谁真正做决定？

谁说话以后其他人会改变意见？

会议结束后：

用户填写观察结果。

这种设计解决一个核心问题：

用户不知道现实世界里应该观察什么。

# 17. Skill Tree

随着使用增加，系统逐渐解锁训练主题。

例如：

**Level 1：事实与解释**

↓

**Level 2：动机与约束**

↓

**Level 3：利益关系**

↓

**Level 4：组织权力**

↓

**Level 5：社会信号**

↓

**Level 6：长期行为模式**

↓

**Level 7：复杂多人博弈**

产品不应该第一天把所有复杂模型给用户。

它应该像训练课程一样逐渐增加认知负担。

# 18. 经典案例系统

《资治通鉴》《史记》《战国策》《红楼梦》等不应该成为单独阅读模块。

正确方式是：

### Case Retrieval

用户现实中遇到：

“上级突然更换负责人。”

系统发现用户正在训练：

**授权 / 信任 / 组织约束**

这时才推荐一个历史案例。

不是告诉用户：

“你的领导就像历史人物 X。”

而是告诉用户：

“这个案例展示了一种值得考虑的机制：公开职责与实际权力可能不同。”

重点学习：

**mechanism，而不是人物类比。**

经典因此成为：

Pattern Library

社会行为模式库。

# 19. 数据结构

随着长期使用，系统逐渐形成四类数据。

### Event

发生过什么事情。

### Person

事件涉及哪些人。

### Relationship

人与人之间是什么关系。

### Prediction

用户曾经做过什么判断。

后期可以进一步建立：

### Pattern

用户经常遇到什么类型的场景。

例如：

授权变化；

冷淡；

表扬；

冲突；

资源争夺；

责任转移；

合作邀请；

突然示好。

最终产品真正有价值的不是“记录了很多事情”。

而是：

**知道用户在哪些模式上判断准确，哪些模式上经常犯错。**

# 20. AI 的角色

AI应该有五种角色。

### Interviewer

帮助用户补充高价值 Context。

### Skeptic

主动挑战用户目前的解释。

### Hypothesis Generator

生成其他可能性。

### Forecaster

帮助把解释转换成可验证预测。

### Coach

根据长期历史发现用户的认知偏差。

AI绝对不应该扮演：

**“读心大师”。**

产品中应该避免：

“他真正的想法是……”

而使用：

“基于当前信息，一种可能解释是……”

# 21. MVP 暂时不做

第一阶段不建议做：

复杂人物关系图；

人格分类；

MBTI；

微表情分析；

聊天记录自动监控；

实时录音分析；

所谓测谎；

“这个人值不值得深交”评分；

人物好坏评分；

大型历史知识库；

复杂博弈模拟。

这些功能看起来酷，但会让产品快速偏离真正目标。

# 22. 第一版界面结构

产品第一版甚至只需要四个 Tab。

### 今天

快速记录事件。

### 事件

过去所有 Event。

### 预测

正在等待现实验证的 Prediction。

### 我的模型

长期发现：

常见偏差；

高准确场景；

低准确场景；

个人模式。

# 23. North Star Metric

核心指标不应该是：

DAU。

也不应该是：

用户记录了多少条。

真正的北极星指标应该接近：

# Completed Learning Loops

即：

**完成“观察 → 判断 → 预测 → 结果 → 复盘”的事件数量。**

因为只有完成整个闭环才真正发生学习。

# 24. 辅助指标

可以观察：

预测填写率；

Outcome 回填率；

完整闭环率；

平均预测置信度；

概率校准程度；

每周复盘率；

用户事实/推断混淆次数变化；

同类型事件判断准确度变化。

高级阶段可以计算：

### Calibration Score

例如用户说：

“70%概率发生”

长期来看是否真的大约 70% 发生。

这比简单“正确率”高级得多。

# 25. 产品成长路线

## Phase 0：人工训练

用户 + ChatGPT。

完全不开发。

先跑 20–30 个事件。

目标：

发现真实使用过程中的摩擦。

## Phase 1：Personal MVP

极简 Web App。

实现：

快速事件记录；

AI结构化；

多假设；

预测；

结果回填；

复盘。

目标：

验证闭环是否真的可以长期坚持。

## Phase 2：Personal Intelligence

加入：

人物模型；

事件关联；

长期偏差识别；

预测校准；

周报。

产品开始真正拥有长期价值。

## Phase 3：Social Reasoning OS

加入：

关系网络；

组织结构；

模式库；

历史案例检索；

场景训练；

模拟推演。

此时产品已经不再只是记录工具。

而是个人：

**Social Reasoning System。**

# 26. 最大产品风险

最大风险不是 AI 分析不准。

而是用户产生：

**“AI 帮我证明我的猜测是对的。”**

因此产品必须天然具有反确认偏误机制。

例如：

系统发现用户连续输入：

“他这样是不是针对我？”

不能顺着分析。

而应该自动加入：

“还有哪些不涉及针对你的解释？”

产品必须训练：

**epistemic humility**

认知谦逊。

# 27. 最终产品愿景

最终我们不是试图让用户成为：

“特别会揣摩别人的人。”

而是让用户逐渐形成一种能力：

面对一个复杂社会事件时，

能够自然完成：

观察事实；

识别上下文；

理解角色；

分析利益；

识别约束；

构建多个解释；

判断概率；

等待证据；

更新模型。

当这个过程经过大量现实训练以后，

其中一部分会自动化。

用户最终表现出来的，就是所谓：

**判断力、识人能力、组织感觉和直觉。**

产品真正训练的不是“人情世故”。

而是：

# Social World Modeling

**对社会世界建立越来越准确的内部模型。**

这里面我刻意做了一个很重要的产品决策：**暂时不定义最终工具长什么样，而先定义“学习闭环”是什么。** 这是因为如果现在直接做“人物关系图 + AI 分析 + 资治通鉴知识库”，十有八九会做成一个看起来很强、实际上你几天就懒得用的东西。

真正下一步应该不是马上写代码，而是我和你先用 **Phase 0 人工版** 跑 10～20 个真实事件。我可以按照这个 PRD 充当完整系统，你只负责把现实事件丢进来。等我们跑出真实使用数据以后，就能进一步产出第二份更重要的东西：**MVP 产品原型 + 页面流 + 数据库结构 + AI Prompt/Agent 架构**。那时候甚至可以直接开始做你自己的第一版产品。
