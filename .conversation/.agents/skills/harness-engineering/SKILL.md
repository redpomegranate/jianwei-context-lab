# Harness Engineering

版本：0.2.0；定位：生产级 Harness 构建规范；状态：候选规范，尚未通过独立行为评估或生产验证。

## 角色与边界

为生产 Agent 的架构、实现、验收和长期运行提供可执行工作流程，而不是充当业务决策者。
默认目标不是“可运行 Demo”，而是给定风险、负载和服务承诺下可受控运行的系统。
产品规模可以小，但安全、数据正确性、恢复和发布门禁不能因 MVP 而省略。
方法参考 bojieli/ai-agent-book 的相关章节，来源映射见 [references/sources.md](references/sources.md)。
这里只提炼工程方法，不背书书中未独立核验的行业数字、产品实现或前沿案例。

Harness 是 Agent 边界内模型之外的运行与治理层；外部数据库与用户属于环境。
Skill 是指导材料，不是执行引擎、权限边界或生产可靠性的证明。
遵守所在平台及项目的上位指令；本 Skill 不授予工具权限，不自动发布或修改线上数据库。

先识别任务：
- **Design**：交付设计、契约和验收方案，不触碰线上状态。
- **Build**：在明确授权的项目范围内实现，并运行可用的验证。
- **Audit**：只读审计现有证据，输出缺口与优先级。
- **Improve**：根据失败轨迹提出候选更新，通过独立门槛后才提升版本。

若用户只说“建立 Harness”，默认以产品 Agent 的生产运行治理为主；
Coding Agent 的开发约束作为实现手段，不得拿开发流程代替运行系统设计。

## 五条原则

1. **先定义成功，再行动**：把需求拆成可观察验收条件，区分功能、过程与安全约束。
2. **上下文足够但最小**：按任务加载资料；将输入证据、用户授权、模型建议明确分离。
3. **关键边界由代码强制**：权限、状态、预算、schema、幂等性不依靠“请不要”。
4. **完成必须有环境证据**：测试输出、数据库状态或可复核结果比模型自述优先。
5. **纠正有限且可回退**：失败留痕、有预算、有终点，候选更新与正式运行分离。

正例：测试未能运行，报告“实现完成、验证阻塞”，提供具体阻塞及未验证范围。
反例：模型认为实现合理，便报告“全部测试通过”。

## 执行流程

### 0. 生产范围与风险基线

先定义数据分类、租户边界、允许的自主动作、最大副作用、峰值负载、依赖与运维责任人。
风险分为只读、可逆写入、高影响/不可逆操作；按动作细分，不能给整个 Agent 笼统授权。
记录面向业务成功的 SLI/SLO、统计窗口、RTO/RPO、容量与预算及发布阻断条件。
未知值留为明确决策项：设计可以继续，生产就绪结论必须阻断，不能猜一个行业通用数字。
为生产标准的每个控制项标出实现、负责人、自动检查、故障演练及证据。

### 1. 勘察与建立契约

读已有项目说明、相关代码、测试配置和当前变更；先检查路径，不猜文件名或命令。
记录任务目标、非目标、可变更范围、已授权动作、验收证据与风险。
简单低风险任务可用几行契约；跨模块、安全或数据变更使用完整模板。
优先复用现有机制，不为“成熟”默认增加多 Agent、向量库、图框架或消息队列。
只有无法从现有材料解决的高影响歧义才向用户提问。

### 2. 设计五要素及强制位置

| 要素 | 必须回答 | 典型实现位置 |
| --- | --- | --- |
| Context | 当前目标、状态、证据和未知是什么？加载什么、不加载什么？ | 上下文构造器、版本化快照 |
| Tools | 输入输出、身份、权限、副作用与失败语义是什么？ | 适配器、JSON Schema、服务端鉴权 |
| Constrain | 哪些动作在什么状态和授权下可以执行？ | 状态机、策略层、数据库约束 |
| Verify | 如何证明动作与结果均符合要求？ | 验证器、测试、状态回读、独立审查 |
| Correct | 重试、暂停、人工接管与回退如何结束？ | 恢复控制器、检查点、补偿流程 |

每条关键规则标记 enforcement：`runtime`、`database`、`ci`、`human` 或 `instruction-only`。
对安全要求仅有 instruction-only 的方案，明确标为未完成，不能称为硬约束。

### 3. 构造可靠的执行循环

采用显式状态：prepared → running → verifying → succeeded；
失败进入 recovering、blocked、failed 或 cancelled，而不是无限循环。
暂停与恢复必须保留任务版本、已完成步骤及下一安全动作；恢复前回读真实状态。

每次外部动作遵循：
1. 读取当前授权、目标资源和最新状态。
2. 校验工具是否真实可用及参数 schema，验证主体身份和资源所有权。
3. 有副作用时建立幂等键；跨系统操作定义失败后的核对与补偿方式。
4. 在明确超时和总预算内执行。
5. 依据结构化返回和必要的状态回读验证结果；HTTP 成功不等于业务成功。
6. 持久化脱敏执行证据，再推进状态。

日志与业务提交之间可能崩溃时，使用事务、outbox 或供应商幂等机制并支持对账。
不要承诺跨系统“恰好一次”；没有幂等能力的写入在结果未知时暂停核对。
并发提交用事务、唯一约束或版本比较防止重复与旧状态覆盖。
并行仅用于相互独立的任务，不让单个读失败取消所有无关工作。

### 4. 明确恢复预算

先按错误类别决定，不盲目重试：
- 参数/schema 错误：给出字段级反馈，允许有限修正；不能静默改变操作语义。
- 暂时性限流/网络故障：在总截止时间内退避；尊重 Retry-After。
- 权限错误：停止该动作，使用所在平台授权流程，不能绕开权限。
- 写入超时/连接断开：先查询执行结果，不能默认失败后重发。
- 业务规则冲突：保持原状态，要求用户或业务流程解决。
- 预算耗尽、取消、重复失败：保存检查点，明确终止或人工接管。

未有生产数据时，可提议初始上限为每个可安全重试操作额外重试 2 次、结构修正 1 次；
这些是本 Skill 的可调整起点，不是书中定律。运行前必须设置总调用数、时限及成本预算。
恢复路径本身不得递归触发相同恢复；终止处理避免再依赖失败中的模型。
模型切换须符合隐私和供应商授权要求，且通过契约兼容验证，不能悄悄扩大数据流向。

### 5. 验证与交付

建立三层证据：
- 确定性：schema、状态机、鉴权、幂等性、预算、数据库约束。
- 行为性：事实忠实性、工具选择、提示注入防护、业务禁区与人工接管。
- 端到端：真实入口到持久化结果，含失败、重启和恢复。

先确认项目真实的测试与构建命令，再执行；不存在的测试记录为缺口。
模型评审可辅助语义质量，但不能裁决授权、替代真实状态或自己批准发布。
禁止删断言、加 skip、伪造日志或降低门槛来让任务“通过”。
合法测试调整应有需求变更依据，并由独立审查者核对；候选自改流程不能改自己的裁判。

完成报告必须列出：
- 实际产物及变更范围；
- 执行的验证、结果及证据位置；
- 未执行的验证与原因；
- 剩余风险、授权要求及下一安全步骤。

### 6. 可观测性与离线改进

记录 run/trace ID、step/span、时间、模型/提示词/Skill/工具版本、状态迁移、
脱敏输入摘要、工具结果类别、重试次数、延迟、token/成本和验证证据引用。
保留简短决策说明和外部动作证据，不要求或存储隐藏思维链。
密钥不进日志；原始私人事件不默认进遥测。定义访问控制、保留期及删除机制。

失败归因定位“首个导致偏离的步骤”，区分根因、连锁症状和不确定性。
在线循环只执行与记录；离线循环用授权且脱敏的数据提炼候选改进。
候选必须有来源、适用条件、反例、版本、回归结果和回退目标。
比较基线与候选时固定任务/工具/环境，对随机输出做多次运行并报告波动；
小样本只用于发现问题，不用于宣称成熟。
安全门槛、保留集、审计日志及稳定备份由独立权限保护。

## 完成定义

Skill 交付 ≠ Harness 实现；Harness 实现 ≠ 生产验证。
使用 production-readiness 模板逐项判断，不能以“试用没有报错”代替生产验收。
缺失关键证据、开放的发布阻断缺陷或未落实的运维责任，结论必须是 NOT_READY。
仅当全部适用门禁通过，才能对指定版本、环境、负载与风险范围报告 READY_FOR_CANARY；
金丝雀观测通过后才能按授权扩大流量。任何 READY 都不是永久可靠性保证。
